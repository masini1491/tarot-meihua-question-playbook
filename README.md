# Tarot × 梅花易數提問設計實戰手冊

一套可重用的 **塔羅（Tarot）＋梅花易數（Meihua Yishu）提問設計方法論**。

本儲存庫不以整理牌義、卦辭或「算得準不準」為主要目的，而是處理更前面的問題：

> **怎麼把一個模糊、混合、容易被解讀污染的問題，改寫成可比較、可追蹤、可驗證、低歧義的占卜題目？**

核心目標是降低以下常見錯誤：

- 同一牌位同時承擔「發生機率、好壞、滿意度、後果」多種功能。
- 多選一題中，把「牌很漂亮」誤當成「該選項機率最高」。
- 尚未確認前提，就在條件式分支中繼續細問數值或時間。
- 因為不喜歡第一次結果而反覆重抽，最後只留下符合期待的答案。
- 塔羅與梅花易數彼此硬投票，而沒有先定義各自負責回答什麼。
- 把「啟動窗口、決策窗口、完成窗口」混成同一個時間點。
- 問題一次塞入過多人物、事件、時間與因果，導致牌位無法唯一對應。

本手冊把占卜視為**象徵性、反思性與結構化推理工具**；現實決策仍應以可驗證資訊、專業意見與實際條件為優先。

## 核心原則

### 1. 先定義「這一張牌到底負責回答什麼」

牌位先有契約，才抽牌。

例如「四個薪資區間各一張」時，必須先決定牌位是在比較：

- 實際落地的相對可能性；或
- 該幅度發生後的品質／滿意度；或
- 該幅度背後的公司意圖。

**不可在同一組牌裡混用。**

### 2. Probability is not Quality

> **「最正面的牌」不必然等於「發生率最高」。**

若題目要比較機率，題目必須明確限制：

> 每張牌只代表該選項「實際發生的相對可能性」，不要解讀該情境本身的好壞、滿意度或象徵品質。

### 3. 先判斷主分支，再問分支細節

錯誤：還不知道會不會升職，就直接問「升職後會加薪多少」。

較佳流程：

1. 先比較「不升／升職」等最終落地型態。
2. 確認最強分支後，再在該前提下問調薪區間。

### 4. 一題只保留一個主要判斷功能

同一題可以有背景，但應只有一個主要輸出，例如：哪個選項最可能、事件如何發展、何時最可能發生、最大阻礙是什麼、某人是否適合作為資訊來源。

若同時要問「會不會、何時、為什麼、好不好、怎麼辦」，通常應拆題。

### 5. 補占是為了消除明確歧義，不是為了追求喜歡的答案

只有在下列情況才優先補占：

- 原題存在可指出的設計缺陷。
- 新的現實資訊改變前提。
- 原結果只能定位大窗口，需要區分事件層級。
- 多個選項牌勢接近，需要以更乾淨的條件重問。
- 已出現真實事件，需要從抽象預測切換成具體事件判斷。

不應因為結果不合期待就重抽。

### 6. 塔羅與梅花易數要先分工，再交叉驗證

預設建議：

- **塔羅**：適合多選一、人物／關係動態、事件流程、阻礙、選項比較、心理與策略層次。
- **梅花易數**：適合事件結構、變化方向、主客關係、動爻轉折、近程應期、突發事件或明確數字／時間起卦。

梅花不是「塔羅結果不夠漂亮時再抽一次」的第二票。

## 建議的題目設計流程

```text
現實問題
  ↓
先寫清楚「要判斷什麼」
  ↓
辨識題型（比較／流程／時間／原因／人物／校正）
  ↓
決定 Tarot、Meihua 或兩者分工
  ↓
定義每一牌位／卦的唯一功能
  ↓
抽牌／起卦
  ↓
先依原契約解讀，不臨時改牌位功能
  ↓
若有明確歧義，再用更窄的新題補占
  ↓
等待現實事件驗證
```

## 與其他專案的差異

GitHub 上已有不少 Tarot／梅花易數的抽牌、起卦、牌義、AI 解讀或 Skill 專案；本 Repo 專注在較少被獨立整理的一層：

> **Question Design / Spread Contract / Follow-up Discipline / Cross-validation Governance**

也就是先把問題問對，再談怎麼解。
